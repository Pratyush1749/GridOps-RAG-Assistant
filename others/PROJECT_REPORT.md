# Enterprise Advanced RAG — GridOps

> A production-grade, end-to-end **Retrieval-Augmented Generation (RAG)** system for
> **electric grid operations**, built incrementally — from a naïve RAG baseline to a
> hardened, cached, and guardrailed pipeline orchestrated with **LangGraph**.

> **Note on accuracy:** every number in this report is measured from the running
> system, not estimated. Where a component is implemented but not wired into a
> request path, or advertised in a diagram but optional, it is called out
> explicitly in [§10 Known Limitations](#10-known-limitations).

---

## 1. Project Title

**Enterprise Advanced RAG with Hybrid Search, ReRanking, CRAG, Self-RAG, Text2SQL, Caching and Guardrails in LangGraph**

A conversational AI copilot for grid operators, distribution engineers and dispatchers.
The system routes natural-language questions into a **RAG pipeline** (documentation
lookup), a **Text2SQL pipeline** (operational data queries), or a **hybrid pipeline**
(when both are needed) — behind a layered security stack and a 5-tier Redis cache.

---

## 2. Aim

Build a RAG copilot that progressively layers in modern retrieval techniques —
Hybrid Search, Reranking, HyDE, CRAG, Self-RAG — combined with **Text2SQL**,
**multi-tier caching**, and a **defense-in-depth security pipeline**, orchestrated
as a stateful, resumable **LangGraph** state machine with **human-in-the-loop SQL
approval**.

The evaluation harness exists to answer one question honestly: *does each advanced
technique actually improve measured answer quality over the naive baseline?*

---

## 3. Domain & Dataset

The domain is electric utility distribution operations: substations feed feeders,
feeders carry transformers, transformers serve customer meters; outages, SCADA
alarms and crew dispatches are the operational event stream.

### 3.1 Structured data (PostgreSQL)

Generated by `backend/scripts/data_pipeline/generate_grid_ops_db.py` (Faker, fixed
seed for reproducibility) into `seed/migrations/003_seed_grid_ops.sql`.

| Table | Rows | Notes |
|-------|------|-------|
| `substations` | 50 | voltage class correlated with substation type |
| `feeders` | 500 | FK → substations |
| `transformers` | 500 | FK → feeders |
| `meters` | 500 | FK → feeders; residential/commercial/industrial |
| `outages` | 500 | severity P1–P4, cause, MTTR, customers affected |
| `scada_alarms` | 500 | FK → transformers; 8 alarm types |
| `crew_dispatch_logs` | 500 | FK → outages; response times |
| **Total** | **3,050** | |

### 3.2 Document corpus (Qdrant)

| Layer | Count | Description |
|-------|-------|-------------|
| Procedural / conceptual | 8 | Hand-authored: substation ops, feeder restoration, transformer overload response, SCADA alarm playbook, outage severity & dispatch, reliability metrics (SAIDI/SAIFI/CAIDI), smart meters, storm response |
| Operational records | 422 | Generated **from the seeded SQL rows** by `generate_grid_ops_docs.py`: 50 substation profiles, 150 outage post-mortems, 100 transformer inspections, 80 feeder summaries, 30 regional monthly reports, 12 storm after-action reports |
| **Total** | **430 files → 562 chunks** | |

Formats are deliberately mixed to exercise the full Docling ingestion path:
187 `.txt`, 101 `.html`, 83 `.md`, 34 `.docx`, 17 `.pdf`.

Because the operational records are generated *from* the database rows, the same
entities (outage #12, transformer `XFMR-00141`, substation `sub-portjesseville-016`)
are addressable through **both** the documents and the SQL tables — which is what
makes the hybrid RAG+SQL route meaningful rather than decorative.

## 5. Architecture

```
Browser (React) ──HTTP+JWT──> FastAPI /api/v1
                                  │
                    security: rate limit → token budget → tiktoken truncate
                              → llm-guard (opt-in) → PII redaction
                                  │
                              LangGraph  ──checkpoints──> PostgreSQL
                                  │
                    route_intent (gpt-4o-mini, Redis-cached)
                    ├── sql / hybrid ──> generate_sql → interrupt() HITL
                    │                     → execute_sql (SELECT-only) → Postgres
                    └── rag ──────────> rag_service.run_rag
                                          embed (OpenAI → local fallback)
                                          dense (Qdrant) | sparse (TF-IDF) | hybrid (RRF k=60)
                                          → cross-encoder rerank
                                          → CRAG grade → Tavily web fallback if < 0.7
                                          → spotlight + hardened prompt → gpt-4o
                                          → Self-RAG reflect (retry if < 0.85, max 2)
                                  │
                    output: moderation + PII redaction → schema validation
```

## 6. Key Modules

| Module | Implementation |
|--------|----------------|
| **Intent routing** | `services/router_service.py` — gpt-4o-mini JSON classifier, Redis-cached 24h |
| **Hybrid retrieval** | `services/vector_store.py` + `sparse_vector_service.py` — dense top-20 + TF-IDF top-20 fused with Reciprocal Rank Fusion (k=60) |
| **Reranking** | `services/reranking.py` — cross-encoder re-scores the top `RERANKER_INITIAL_TOP_K` (20) |
| **HyDE** | `services/hyde.py` — 3 hypothetical answers generated, embedded, searched, deduped |
| **CRAG** | `services/crag.py` — grader LLM scores retrieved context; below `CRAG_RELEVANCE_THRESHOLD` (0.7) falls back to Tavily |
| **Self-RAG** | `services/self_reflective.py` — critic scores the answer; regenerates with a refined question while score < `REFLECTION_MIN_SCORE` (0.85), max 2 retries |
| **Text2SQL + HITL** | `services/sql_service.py` (schema-aware generation, `SELECT`-only validation) + `core/graph.py` `interrupt()` approval gate |
| **Caching** | `services/query_cache_service.py` — 5 tiers (embedding 7d, intent 24h, sql_gen 24h, sql_result 15m, rag_answer 1h), keyed by SHA-256 **and embedding model** |
| **Security** | `security/` — see README §4 for the per-layer default-on/off table |

## 7. Evaluation

Harness: `backend/eval/`, 40 golden questions in `seed_questions.yaml`, scored with
RAGAS. Every factual golden was verified against the live database before being
written (e.g. "51 P1 outages", "92.1 min average crew response").

Golden coverage: 5 baseline, 4 rerank, 4 HyDE, 4 CRAG, 4 Self-RAG, 8 SQL,
5 hybrid RAG+SQL, 2 security, 4 "wild" (facts buried mid-document).

The document corpus includes a 1,200-document out-of-domain distractor set
(`generate_noise_corpus.py`) - 70% *near-domain* (telecom/water/datacenter/HVAC/
rail/fleet incident reports sharing grid-ops vocabulary like "outage", "P1",
"crew dispatched") and 30% *far-domain* (recipes, travel, HR policy) - so naive
retrieval has real noise to fail against, not just an all-signal corpus. Total
corpus: 429 signal docs + 1,200 noise docs → 1,761 chunks.

### Measured results (1,761-chunk corpus, `service` mode)

| Metric | naive | hybrid+rerank+crag (crag goldens only) | all features |
|--------|-------|------|-----|
| Faithfulness | 0.688 | 0.852 | 0.619 |
| Context precision | 0.518 | 0.487 | 0.574 |
| Context recall | 0.562 | 0.481 | 0.568 |
| Answer relevancy | 0.523 | 0.650 | 0.538 |

**The `all`-features profile is not a uniform win over `naive`** — this is the
honest finding, not a flattering one. Diffing the two runs (`eval/diff.py`)
row-by-row: CRAG's web fallback produced a real, measurable lift on `q-014`
(faithfulness 0.00 → 0.67, answer relevancy 0.00 → 0.73, a genuine out-of-corpus
question rescued by Tavily). But HyDE **hurt** `q-010` badly (faithfulness
1.00 → 0.29) — forcing hypothesis-based retrieval on a question that plain
dense search already answered well introduces speculative content that can
drift from a direct match. Net effect on aggregate faithfulness across the 27
scoreable goldens: **down** (0.688 → 0.619), while precision/recall/relevancy
moved up slightly. Advanced retrieval techniques are not free — they trade
robustness on hard queries for occasional regression on easy ones, and only
per-golden diffing surfaces that trade-off.

13 of 40 goldens (the `sql`/`hybrid` intents) are skipped in `service` mode —
run with `--mode api` to score all 40 (see §8, item 4, and §10).

Run `make eval` (baseline + all-features + diff) or an individual profile via
`uv run python -m eval.run_ragas --profile <name> [--mode service|api]`.
`eval/diff.py` reports the per-metric and per-golden delta between two runs.

## 8. Engineering Problems Solved

Five bugs found and fixed via the eval harness are worth recording, because they
are the kind that silently destroy RAG quality while everything still "works":

1. **Non-idempotent ingestion.** `upsert_chunks()` assigned a random UUID per point,
   so re-running the seed script duplicated the entire collection instead of
   overwriting it (3,747 points for 1,218 unique chunks — every chunk stored ~3×).
   Fixed with a deterministic `uuid5(namespace, source::text)` point ID.

2. **Model-blind embedding cache.** The embedding cache was keyed on text alone.
   Once vectors had been cached from the local MiniLM fallback (384 real dims
   zero-padded to 1536), a later run with a working OpenAI key kept serving those
   stale low-quality vectors — so a rich 1536-d query vector was being compared
   against degenerate padded document vectors, producing near-random similarity
   (0.03–0.07, flat). Fixed by namespacing the cache key by embedding model.

3. **Unparsed structured output.** The system prompt asks the model for
   `{"answer", "sources", "confidence"}` JSON, but the raw string was stored
   directly as the answer — so users and RAGAS both saw a JSON blob instead of
   prose. Fixed by wiring up the previously-dead `output_validator.validate_with_retry`.

4. **`ChatResponse.metadata` was silently empty for every live API response,
   for every intent.** `GraphState` (the LangGraph state schema) never declared
   a `metadata` key, and LangGraph drops any key a node returns that isn't in
   the schema — no error, no warning, just gone. `api/query.py:_build_response`
   read `result.get("metadata", {})`, so it always got `{}` and fell back to
   `ResponseMetadata()`'s defaults: `route` always showed `"rag"` regardless of
   actual intent, and `retrieved_chunks` was always empty even when five real
   chunks had been retrieved. **This was invisible from `service`-mode eval**,
   which calls `rag_service` directly and never goes through the graph's
   response-building code at all — only driving the real HTTP endpoint
   (`--mode api`, item 4 above) exposed it. Fixed by reconstructing
   `ResponseMetadata` in `_build_response` from the individual fields
   `GraphState` *does* declare (`intent`, `chunk_previews`, `reflection_*`,
   `rag_cache_hit`/`sql_cache_hit`) instead of a dropped nested blob.

5. **The hybrid pipeline's RAG half never saw real document text.**
   `retrieve_rag()` built its "retrieved documents" context from
   `response.sources` — a deduplicated `list[str]` of *filenames only* — via
   `type("Chunk", (), {"text": s, "source": s, ...})`, i.e. a fake chunk whose
   `.text` was literally the filename. Every hybrid-routed answer's prompt
   therefore said "here are the retrieved documents: `outage-postmortem-0012.txt`"
   with no actual content, while still combining that with real SQL rows and
   producing a plausible-sounding answer (from the SQL data plus the model's own
   inference) - which is exactly why this stayed hidden: the answers still read
   fine, but RAGAS faithfulness/context-precision/recall on hybrid-routed
   goldens sat at a flat 0.00 with no error. Fixed by threading the real
   `RetrievedChunkPreview` objects (text/source/score) `rag_service` already
   computes through to the spotlighted context, `chunk_previews`, and `sources`.

Both #4 and #5 were found in the same few minutes of first actually exercising
`--mode api` end-to-end - the strongest evidence in this project that
service-mode eval and manual spot-checks are not a substitute for driving the
real request path.

After the first three fixes the naive baseline moved from `faithfulness 0.022 /
context precision 0.0 / recall 0.148 / relevancy 0.029` to the numbers in §7.

## 9. Learning Outcomes

- Orchestrating a resumable, checkpointed agent graph with human-in-the-loop gates
- Building and measuring a hybrid retrieval stack rather than assuming it helps
- Using an eval harness as a debugging instrument, not just a scoreboard
- Defense-in-depth for LLM applications: input validation, spotlighting, output
  validation, budget/rate controls
- Cache correctness: cache keys must encode every input that changes the value
  (the embedding-model bug above is the canonical example)

## 10. Known Limitations

Stated explicitly so the code and this report do not disagree:

- **`--mode api` needs a running server and seeded credentials.** It logs in as
  `EVAL_API_USERNAME`/`EVAL_API_PASSWORD` (default the seeded admin) and
  auto-approves every Text2SQL `interrupt()` it hits, which is correct for
  unattended eval scoring but means it should not be pointed at a shared/prod
  server - it will execute whatever SQL the model generates.
- **Two security layers are opt-in.** L2 (llm-guard input scan) and L7a (llm-guard
  output moderation) are gated behind `ENABLE_SECURITY_SCANNERS=true` because they
  download large models. Regex injection guards, PII redaction, rate limiting,
  token budget, spotlighting and schema validation are always on.
- **Security goldens don't test the L1 gate directly.** Both `service` and `api`
  mode see the L1 Pydantic regex guard's HTTP 422 (api mode surfaces it as a
  scored "blocked" refusal; service mode never sends the request over HTTP at
  all). The `forbidden_keywords` check still verifies no prompt/config leakage
  either way.
- **Sparse retrieval is TF-IDF, not BM25, and not Qdrant-native.** The index is
  rebuilt in-process on every sparse/hybrid query by scrolling the collection —
  correct but O(collection) per query, and the main scaling bottleneck now that
  the collection holds 1,761 chunks instead of 24.
- **The graph re-enters the service layer for `rag` intent.** `core/graph.py`'s
  `generate_answer` delegates to `rag_service.run_rag`, which classifies intent
  a second time. LangGraph's clearly load-bearing role is the `sql`/`hybrid`
  HITL approval flow and the `retrieve_rag` node feeding `_generate_hybrid_answer`.
- **`DocCacheService` / `app/storage/` are unused.** Implemented (local + S3
  backends) but not wired into the upload path.
- **Noise ratio is ~74%, not the 95% the original design called for.** The
  distractor corpus (`generate_noise_corpus.py`) is 70% near-domain (telecom /
  water / datacenter / HVAC / rail / fleet operations - sharing the words
  "outage", "alarm", "crew", "P1" without answering any grid question) and 30%
  far-domain. Near-domain noise is what actually forces the reranker to
  discriminate; far-domain noise is trivially separable by embedding.
- **"All features enabled" is not strictly better than naive** (§7) - HyDE and
  Self-RAG can regress already-easy queries even as CRAG rescues genuinely
  out-of-corpus ones. Treat feature flags as per-query-type tuning knobs, not
  a strict quality ladder.
- **RAGAS numbers in the Eval Dashboard screenshot** are a point-in-time snapshot
  (`20260903T052105Z_all.json`) - re-run `make eval` for current numbers as the
  corpus/goldens evolve.

---

## 11. Possible Extensions

- Push the noise ratio from ~74% toward the original 95/5 design target
- Move sparse retrieval to Qdrant-native sparse vectors (or a real BM25 index),
  and stop rebuilding the TF-IDF index on every query
- Collapse the graph's double entry into `rag_service` (intent is classified twice)
- GraphRAG over asset relationships (substation → feeder → transformer → meter)
- Streaming responses; per-request cost/latency telemetry in the metadata pane
